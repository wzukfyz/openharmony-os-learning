# 五天先导课设计

## 贯穿场景

五课沿用“应用读取并显示一段本地文本”。它只用于理解职责，不表示所有设备、应用框架或文件访问都经过完全相同的调用链。示意图是教学抽象，不是完整真实调用跟踪。课程无需安装环境或读源码；每课阅读预计 5～15 分钟，思考练习约 1～3 分钟。

## Day001：我们要学习的 OpenHarmony 是什么？

- **目标：** 说明 OpenHarmony 项目定位及本课程学习对象。**前置：** 无。
- **提纲：** 开源项目与操作系统平台；面向多类智能终端；本课程关注标准系统内核机制；与商业 HarmonyOS 产品体系不是同一概念。
- **术语：** 开源项目（公开源码并按许可协作）；操作系统平台（由内核及用户空间组件共同构成）。名称相似不代表项目边界相同。
- **例子/简图：** 从“应用显示本地文本”点出需要理解操作系统如何提供资源服务，不画完整架构。
- **练习：** 用一句话分别写出本课程学什么、不学什么。
- **自检问题：** OpenHarmony 与内核是什么关系？本课程与普通应用开发课有什么不同？
- **自检答案要点：** 课程研究内核机制及 OpenHarmony 标准系统内核集成，不是普通应用开发课；OpenHarmony 是开源项目，不应与商业产品混称。
- **预计时间：** 阅读 8～10 分钟；思考 1～3 分钟。
- **衔接：** 下一课定位内核在整个系统中的位置。
- **依据：** OpenHarmony 项目概览；核验日期与限制见[资料索引](../04_资料索引/官方资料索引.md)。

## Day002：OpenHarmony 不只有内核

- **目标：** 在简化分层中定位内核。**前置：** Day001。
- **提纲：** 应用层发起用户需求；框架和系统服务提供较高层能力；内核提供进程、内存、文件等基础机制；不同层通过接口协作。
- **术语：** 用户空间与内核空间主要描述地址空间及其访问边界；用户态与内核态描述执行权限，二者相关但不能互作定义。本课只建立边界直觉，具体地址空间与权限机制后续解释。分层图不表示每次操作都逐层经过所有模块。
- **例子/简图：** 应用 → 框架/系统服务 → 内核 → 资源；显示文字的布局、字体等逻辑通常由上层负责，内核可能通过图形驱动等参与设备访问，不把界面展示全归给内核或断言其完全不参与。
- **练习：** 将“选择字体显示文字”与“管理文件读取所需资源”放到更合适的职责层。
- **自检问题：** 为什么不能把 OpenHarmony 的全部能力叫作内核能力？文本显示中，上层逻辑与内核资源机制如何分工？
- **自检答案要点：** 界面展示通常由框架/应用处理；内核提供资源管理机制。两者协作但职责不同。
- **预计时间：** 阅读 10～12 分钟；思考 1～3 分钟。
- **衔接：** 不同设备可部署不同内核，下一课说明路线选择。
- **依据：** 项目概览记载内核、系统服务、框架、应用的分层；索引标明使用边界。

## Day003：OpenHarmony 为什么有多种内核？

- **目标：** 理解本路线聚焦标准系统 Linux 的理由。**前置：** Day002。
- **提纲：** 设备资源和系统类型不同；官方文档列出 LiteOS-M、LiteOS-A 与 Linux 等路线；内核选择受设备形态和产品配置影响；标准系统内核学习目标指向 Linux，不代表其它内核不重要。
- **术语：** 轻量/小型/标准系统是 OpenHarmony 文档中的系统类型；LiteOS-M、LiteOS-A 是不同适用形态的内核路线，具体适配以目标版本资料为准。
- **例子/简图：** 资源极受限设备与标准系统在需求上的差异；不将其概括成单一性能排名。
- **练习：** 判断“所有 OpenHarmony 设备必须使用 Linux”是否成立，并解释。
- **自检问题：** 所有 OpenHarmony 设备是否必须使用 Linux？本课程为什么选择标准系统 Linux 路线？
- **自检答案要点：** 不成立；官方资料描述多内核设计。学习路径选择 Linux 是因为目标聚焦标准系统，不意味着其他内核无价值。
- **预计时间：** 阅读 8～10 分钟；思考 1～3 分钟。
- **衔接：** 下一课观察一个普通请求与内核服务的关系。
- **依据：** 内核文档目录和内核子系统说明；其中分支/版本细节会变化，见资料索引。

## Day004：一次普通操作，内核做了什么？

- **目标：** 区分应用请求、内核资源管理与结果返回。**前置：** Day002。
- **提纲：** 应用提出读取需求；经受控接口请求系统能力；内核及相关系统组件协调文件和内存等资源；结果返回后由应用或框架显示。
- **术语：** 系统调用是用户程序请求内核服务的一类受控接口；不是每个高层操作都与一次系统调用一一对应。
- **例子/简图：** 应用读取文本 →（受控请求，教学抽象）→ 文件/内存相关机制 → 数据返回 → 界面显示。图不代表完整调用栈或具体 API。
- **练习：** 将“选择要显示的颜色”“验证并读取文件数据”“显示字符”分别归入可能职责，并指出实际实现可能跨层。
- **自检问题：** 读取和显示文本是否等于一次系统调用？应用为什么需要受控接口来访问资源？
- **自检答案要点：** 内核管理受保护资源并提供机制；界面逻辑主要在上层。应用不能任意访问资源，因为权限边界保护系统与其他进程。
- **答案补充：** 高层操作可能涉及多次系统调用，也可能部分由用户空间缓存处理，不是一一对应关系。
- **预计时间：** 阅读 10～12 分钟；思考 1～3 分钟。
- **衔接：** 下一课把理解转成一年学习与贡献的实际路径。
- **依据：** Linux 官方文档总入口仅作后续机制学习入口；此处为教学概念，不引用具体调用链实现。

## Day005：一年之后，怎样参与内核贡献？

- **目标：** 说出从观察现象到社区评审的贡献准备过程。**前置：** Day001–004。
- **提纲：** 先建立 Linux 通用机制；练习复现和证据记录；阅读 OpenHarmony 目标分支及配置；从文档、测试或小缺陷开始；提交前验证并回应评审。
- **术语：** 复现（按明确步骤再次观察到问题）；回归验证（确认修改后目标问题改善且相关既有行为未受损）。
- **例子/简图：** 观察 → 最小复现 → 定位 → 小范围修改 → 验证 → 评审；不是保证合入的流水线承诺。
- **练习：** 对“读取文件时结果异常”，写下复现记录最少应包含的三项信息。
- **自检问题：** 最小复现记录至少包含什么？为什么看懂源码仍不足以证明补丁正确？
- **自检答案要点：** 环境/版本、可复现步骤、预期与实际结果；看懂概念不等于证明补丁正确。
- **答案补充：** 正确性还需修改依据、针对问题的验证及相关回归测试；是否合入取决于目标社区评审。
- **预计时间：** 阅读 8～10 分钟；思考 1～3 分钟。
- **衔接：** Day006 起建立内核概念，Day007 做首周回顾。
- **依据：** OpenHarmony 贡献流程当前入口可参考，但仓库要求可能不同；实际贡献前重新核对目标仓库。

## 编写正文时的统一约束

每篇正文建议 600～1200 字，目标唯一，术语首次出现就地解释。先导课不要求安装、记忆版本号、产品数量或组织名单，不展开调度算法、页表实现或源码。官方资料核验情况见[索引](../04_资料索引/官方资料索引.md)。

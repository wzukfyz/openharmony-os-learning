## 内容编写与阅读形式

采用 **Markdown 编写与 Git 管理，自动生成 HTML 负责阅读** 的方式。Markdown 是课程内容的唯一来源，修改课程只改 Markdown，再重新生成阅读版，避免维护两份正文。

HTML 阅读版提供统一字号、行宽和行距，以及长文目录、深浅色模式、手机适配、上下课导航和重点样式。正文继续只有摘要与正文，不显示阅读时间或管理字段；目录和主题切换由阅读页面外壳提供。

同时为每篇课程自动生成 **`课程文件名_分享.html` 单文件分享版**，输出至 `_site/share/`。页面将 HTML、CSS、JavaScript 三合一，必要本地图片以数据 URI 内嵌；只发送这一个文件即可用浏览器离线阅读，保留页内目录、重点样式、深浅模式与手机适配。分享版不依赖同目录资源或其他课程文件，官方外链仅作可选查阅入口，不影响离线阅读正文。

生成工具已实现（需要 Python 3.9 或更高版本；依赖为 markdown-it-py、bleach 和 tinycss2，具体版本见 `tools/requirements.txt`）。安装依赖并构建：

```bash
python -m pip install -r tools/requirements.txt
python tools/build_reading.py
```

普通站点输出在 `_site/`：首页为 `_site/index.html`，课程页为 `_site/lessons/Day001.html` 等，可直接双击首页离线阅读。每课另生成 `_site/share/课程文件名_分享.html`，例如 `_site/share/Day001_我们要学习的OpenHarmony是什么_分享.html`，可单独发送。

构建只读取 `01_每日学习/` 中实际存在的 `DayNNN_*.md`，不会为计划课程生成空页。工具、模板、样式、依赖定义和构建生成的 `_site/` 阅读站均应纳入 Git 管理，便于后续发布为网页。更新课程 Markdown 后重新构建并纳入生成页面。浏览器桌面/手机人工视觉检查和独立文件断网检查尚待人工审核；自动化测试与成功构建不等于这些项目已验证。

运行自动化检查：

```bash
python -m unittest discover -s tools/tests -v
```

## 适合谁

- 学过大一程序设计基础，能读写简单 C/C++ 程序，接触过指针、结构体和函数。
- 会使用 Linux 基础命令、文件路径及编译运行程序的方法。
- 对操作系统可以没有基础，也可以学过概念但尚未读过内核源码。
- 希望理解通用内核机制，最终参与 OpenHarmony 标准系统相关开发。

不要求事先精通汇编、计算机组成原理或全部 C 语言细节。必要知识会在对应主题前引入；不重复讲授变量、循环等编程入门内容。

## 我们学习什么

```text
认识 OpenHarmony 与内核定位
        ↓
观察程序如何请求操作系统服务
        ↓
Linux 系统调用、进程、调度、内存、VFS 与同步
        ↓
构建、调试、测试和缺陷复现
        ↓
OpenHarmony 标准系统的内核配置、补丁与集成
        ↓
专题学习、小型贡献与社区评审
```

课程不以单片机、外设控制和板级驱动为主线。OpenHarmony 并非只有内核，课程也会区分 Linux 内核、系统服务、应用框架以及商业 HarmonyOS 的不同定位。

## 建议学习路线

以 365 天为完整目标，前 180 天形成基础闭环。月份是建议节奏，不绑定自然日期；具体每日选题在编写课程总目录时细化。

| 建议阶段 | 主题 | 主要成果 |
| --- | --- | --- |
| 第 1 月（含先导课） | 内核认知与行为观察 | 分清程序、进程、内核，观察系统行为 |
| 第 2 月 | 系统调用与内核入口 | 跟踪一次用户程序请求，认识源码结构 |
| 第 3 月 | 进程与线程 | 理解创建、退出、资源共享和任务对象 |
| 第 4 月 | 调度与时间 | 解释阻塞、唤醒、切换及时间机制 |
| 第 5 月 | 虚拟内存 | 理解地址空间、缺页、映射与写时复制 |
| 第 6 月 | 文件与 VFS | 串联文件打开、读取与关闭 |
| 第 7 月 | 并发与同步 | 理解竞态、锁和对象生命周期 |
| 第 8 月 | 构建、启动与调试 | 运行实验内核，形成定位问题的方法 |
| 第 9 月 | 测试与缺陷复现 | 运行测试，形成可复现的问题记录 |
| 第 10 月 | OpenHarmony 内核集成 | 理解内核基线、配置、补丁与构建关系 |
| 第 11 月 | 专题源码与补丁阅读 | 聚焦调度、内存、VFS 或测试等一个方向 |
| 第 12 月 | 贡献实践与复盘 | 准备小型贡献，记录验证和评审过程 |

构建与调试在第八阶段系统讲解，但实验从前期就开始：先观察普通 Linux 的行为，再进入实验内核；不必先等待完整 OpenHarmony 构建环境就绪。

## 每天怎样学

1. 围绕一个主要问题阅读，理解概念背后的原因与机制。
2. 在正文的例子和情境推理中检验自己能否解释因果、迁移到新场景。
3. 需要运行观察或扩展实践时，按独立实验手册执行并记录实际环境和结果。

每周安排复习或自测。漏学后从下一篇继续，不要求追赶自然日期，也不把连续打卡作为掌握知识的证据。

### 时间与能力预期

正文不标阅读时间或阅读负担；内部阅读节奏只是规划，真实时长和理解难度需通过学习者试学确认。只读也能逐渐建立知识框架；进入构建、测试和贡献阶段，需要实际运行、排错和验证的时间。

半年目标是理解常见机制并完成基础实验；一年目标是具备准备一份小型贡献的能力。进度随实践投入调整，不承诺固定时间独立开发或补丁必然被合并。

## 如何判断学会了

学习记录应区分“阅读完成”“实验完成”和“验收通过”：

| 检查点 | 能力证据 |
| --- | --- |
| 基础认知 | 用自己的话解释程序、进程、Shell 与内核的区别 |

## 本地版本管理

Git 仓库根目录为本目录。交接记录统一位于 `交接文档/YYYYMMDD_HHMMSS_交接文档.md`，通过任务编号和状态区分当前任务与历史记录。执行模型先阅读指定交接文档；其中的任务路径默认相对于本根目录，不相对于 `交接文档/`。Markdown 可点击相对链接仍按文件所在目录解析。

交接文档目前按 `.gitignore` 规则保留在本地，不纳入后续常规提交；需要跨机器保存时应另行备份该目录。

空目录中的 `.gitkeep` 仅用于保留课程目录结构，不代表课程正文；写入实际资料后可移除对应标记。

在本目录执行 `git status` 查看修改，`git diff` 查看未暂存修改，`git diff --cached` 查看暂存内容，`git log --oneline` 查看回档基线。初次提交后的新增文件需先用 `git status` 识别；普通 `git diff` 不显示未跟踪文件内容。恢复文件前先确认目标提交与需要保留的改动。

### AI 协作与规范维护

AI 可协助规划课程、起草与复审文档、检索资料及维护阅读工具。开展具体任务前，应先阅读根目录 `AGENTS.md` 和指定的任务交接，确认授权范围、交付物及验收标准；关键技术事实回到官方资料、源码和测试核对。模型自检或自动化构建不能代替人工内容复审、真实学习者试学或尚未执行的产品验证。

根目录 `AGENTS.md` 是项目长期有效的协作约定，涵盖课程质量、资料核验、AI 决策与执行交接、Markdown 与阅读站的维护边界。**将它保留在 Git 中，能让仓库的协作者和 AI 在克隆项目后获得同一套规则；规范变更也能随提交被审查、追踪历史和恢复。**这样，工作方式不只依赖某台机器上的本地提示、某次对话记忆或某个模型的默认行为。

`AGENTS.md` 保存稳定、可复用的项目规则；`交接文档/` 记录单项任务的目标、范围、状态和执行结果，当前按 `.gitignore` 保留在本地。不要把凭据、私人信息或临时对话原文写入项目规范或提交到仓库。

**课程追求：每天解决一个小问题，每周连接一组知识，每个阶段留下可验证的成果。**

# 五天先导课设计

## 共用标准与贯穿场景

本设计用于正文编写与后续复审，不是课程正文。Day001～Day005 每篇保留一个主要目标，以两至三个紧密相关知识点形成解释链；正文按当前规范为 1500～2000 字，另配 300～600 字摘要。课文无需设备、环境、运行命令或源码。正文头部不放阅读时间、阶段、前置、源码或实验状态；阅读节奏仅作内部规划，实际时长需靠学习者试学检验。写作优先采用短段落和直接表述，删除重复背景及不必要的反向限定；插图明确承担的教学任务，并由正文解释，不以图代文。

贯穿场景为“一个应用读取并显示一段本地文本”。情境用于跨课推理，不声称所有设备、系统服务或应用使用相同调用链。架构图须标为职责示意；文件读取图须标为教学抽象。五课避免复述同一段通用背景：Day001 讲清项目对象，Day002 解释层次缘由，Day003 分析内核选择，Day004 解释文件请求机制，Day005 建立贡献证据方法。

重要概念、因果结论和易混淆边界适度用 Markdown 加粗、下划线或少量红色标记强调。标记与相邻词句间保留空格，并检查最终网页渲染。不得整段加粗或用颜色取代解释；红色渲染可能不一致，须确保加粗/下划线仍能表达重点。正文只设置摘要和正文两个一级板块，思考推理、结论和资料引用自然融入正文。

配图按内容选择静图、动图、文本图或表格。图前提出问题，图后解释关系、符号和省略范围；箭头、颜色和动效都需有明确含义。保留可编辑源、导出物及许可信息，引用使用本地相对路径，并按当前网页构建器实际支持的格式验证。工具和风格保持可替换，不强制安装任何 skill。

## Day001：我们要学习的 OpenHarmony 是什么？

- **主要目标：** 解释 OpenHarmony 项目与内核的层级关系，并说明本课程为什么以 Linux 通用内核机制为主线。
- **解释链：** 多类终端需要共用的资源管理能力 → 操作系统平台由内核与上层组件构成 → 项目、内核、发行/产品不是同一层概念 → 课程对准标准系统 Linux 内核而非整个商业产品开发。
- **知识支撑点：** 项目分层；开源项目与基金会治理；可核验的发布背景；项目公开、贡献和产品交付边界。
- **背景事实边界：** 官方项目概览称 OpenHarmony 由开放原子开源基金会孵化与运营；官方 1.0 发布说明记载 2020-09-10 为首次发布，并将 1.0 标记为停止维护，这只说明该历史版本，不推断整个项目停止演进。基金会目录当前列出贡献方但捐赠方栏空白，不据此推断完整法律交易或历史上从未捐赠。
- **配图建议：** 一张关系图并列项目、平台软件、内核和产品；另一张范围对照图区分 OpenHarmony、Linux 内核、Linux 发行版及商业 HarmonyOS，并标出本课路径。图不替代正文、也不制造产品实测调用链。
- **情境与理解证据：** 用终端软件的组合背景说明项目/内核/产品为何容易混淆；读者可判断一条新事实属于哪个对象，并解释“学 Linux 内核通用机制”不等于“OpenHarmony 就是 Linux 发行版”。
- **资料入口：** OpenHarmony 项目概览、OpenHarmony 1.0 发布说明、开放原子开源基金会项目目录、官方资料索引。
- **配图建议：** 一张关系图并列项目、平台软件、内核和产品；一张范围对照图区分 OpenHarmony、Linux 内核、Linux 发行版及商业 HarmonyOS，说明本课程的学习路径。只画资料支持的关系，不把结构图画成调用流程。

## Day002：OpenHarmony 不只有内核

- **主要目标：** 解释分层如何减少重复并隔离变化，在文本读取与显示中定位各层的典型职责。
- **解释链：** 应用各自操作硬件导致重复和权限风险 → 通过接口把稳定共性下沉 → 库/框架/系统服务/内核抽象不同范围的问题 → 变化可局部化但仍须维护接口兼容。
- **知识支撑点：** 抽象是稳定能力与隐藏实现细节；应用层、框架层、系统服务层和内核层区别；显示驱动参与与上层显示策略的边界；实际流程并非固定逐层穿行。
- **情境与理解证据：** 对比文本布局、窗口协调、文件访问和设备访问；让读者判断什么变化应由应用、框架、服务或内核吸收，并允许根据真实产品实现说明“跨层”。
- **避免误解：** 分布式软总线等系统服务不是内核功能；图形驱动可能处在内核参与设备访问的路径中，因此不说显示完全与内核无关。
- **资料入口：** OpenHarmony 项目概览及官方资料索引。

## Day003：OpenHarmony 为什么有多种内核？

- **主要目标：** 依据设备和任务约束解释内核路线差异，并说明本课程聚焦 Linux 的范围理由。
- **解释链：** 产品在资源、时限、隔离和软件功能方面有不同约束 → 内核设计在这些目标间取舍 → LiteOS-M、LiteOS-A、Linux 服务的场景不同 → 标准系统目标决定课程选 Linux，而非抽象排名。
- **知识支撑点：** RTOS 是实时操作系统，实时强调规定时限内可预测响应而非平均速度最快；资源受限与丰富通用能力的取舍；Huawei LiteOS 与 OpenHarmony LiteOS-A 的官方演进关系；Linux 上游长期公共开发与生态；OpenHarmony Linux 基线及产品适配仍需区分。
- **情境与理解证据：** 用传感器期限任务和文本显示任务对照读者关注指标；读者能反驳“所有 OpenHarmony 设备必须使用 Linux”和“实时内核总是更快”。
- **资料入口：** OpenHarmony 内核目录、内核子系统说明、LiteOS-M/LiteOS-A README、Linux 官方 6.x README。

## Day004：一次普通操作，内核做了什么？

- **主要目标：** 解释一次文件读取中受控请求、文件描述符、缓冲区、数据和返回值的关系。
- **解释链：** 普通函数调用与系统调用不同 → 请求内核管理的资源需受控边界 → 打开建立引用 → 读取把数据放入调用者缓冲区并报告实际数量/错误 → 关闭结束使用。
- **知识支撑点：** 系统调用及库包装；文件描述符是进程引用编号而非内容；返回数据与返回值不同；部分读取、错误检查、关闭；缓存和文件系统差异意味着 `read()` 不等于磁盘访问。
- **情境与理解证据：** 读者能按“打开—读取—检查—使用数据—关闭”说明因果，并解释为什么普通整数计算通常不需系统调用、一次高层操作不等于一次系统调用。
- **避免误解：** 不讲入口汇编或内核函数；不说每次读取都必然访问磁盘；Linux man-pages 用于一般 Linux 接口事实，不外推为某 OpenHarmony 产品调用链。
- **资料入口：** Linux man-pages `syscalls(2)`、`open(2)`、`read(2)`。

## Day005：一年之后，怎样参与内核贡献？

- **主要目标：** 解释从观察问题到提交可复核改进的证据链。
- **解释链：** 先界定对象和版本 → 区分上游 Linux、OpenHarmony 公共基线、产品配置与平台补丁 → 用最小复现识别问题归属 → 判断改文档还是实现 → 提交修改依据和验证范围 → 接受评审。
- **知识支撑点：** Linux 上游与 OpenHarmony 集成不是同一源码状态；OpenHarmony 公共补丁、产品配置和厂商适配层次；文档准确性问题与实现缺陷的证据区别；通用 Linux 验证不等于 OpenHarmony 产品验证。
- **教学案例：** 虚构文档把“请求最多读取 N 字节”误写为“必定读取 N 字节”。示范核对 Linux `read(2)`、判断是说明错误而非已证实实现缺陷、拟定修正文句、限定验证范围；清楚标为教学假设，不伪造真实 bug、日志、PR 或社区认可。
- **资料入口：** OpenHarmony 贡献流程、Linux 内核开发流程与补丁指南；贡献操作规则随仓库变化，实际贡献前重新核对。

## 递进与复审检查

五课沿同一文本情境逐渐增加解释深度，但每篇须新增不同知识：Day001 项目对象，Day002 分层动因，Day003 路线选择，Day004 系统调用与文件读写，Day005 贡献证据链。复审时检查每个结论是否有“为什么—如何发生—例子/反例”支撑，正文中重要术语是否首现即解释，粗体/下划线/红色是否克制有效，历史是否服务本课目标。字数统计和目录格式通过不能替代教学充分性审查或真实学习者试学。

# Day005：一年之后，怎样参与内核贡献？

> 阶段：先导课｜前置：Day001～Day004（依次完成本目录前四课）
>
> 阅读：预计 5～10 分钟（待试学）｜微练习：约 3 分钟｜扩展实验：无
>
> 环境：无需环境；本课无运行实验
>
> 源码基线：不涉及源码解读

## 今天要解决的问题

理解了内核概念，距离提出一项可靠改进还有多远？今天把课程路线连到贡献过程，并区分“看懂”与“验证过”。

## 学习目标

读完后，能按顺序说出从观察问题到接受社区评审的基本环节，并知道初次贡献可以从哪里开始。

## 核心解释

课程不会因为读完一篇文档就直接跳到修改内核。我们先观察系统行为，发现值得追查的现象；再写清环境、版本、复现步骤、预期结果和实际结果，尽量形成别人也能重复的最小例子；之后查阅目标版本源码和测试，定位原因，尝试小范围修改并回归验证；最后按目标仓库当时的规则提交，由社区评审。

```text
观察 → 最小复现 → 定位原因 → 小范围修改 → 验证 → 社区评审
```

**复现**是按明确步骤再次观察到同一问题；**验证**是用适当证据检查修改是否解决目标问题，并确认相关行为没有被破坏。源码看起来合理，不等于行为已经正确；验证范围也要说清楚，例如只在某个 Linux 虚拟机上通过，不等于已验证 OpenHarmony 产品设备。

第一次参与不必从大型功能开始。文档修正、补充测试或修复边界明确的小缺陷，都可能是合适入口。关键是修改有依据；针对缺陷，应能复现问题并提供可信验证；针对文档，应核对来源和示例。提交 PR（Pull Request，即请求维护者评审并合入修改）后，也需要回应评审意见。是否合并由项目评审决定，学习成果不只看 PR 是否合并；成为 Committer（拥有相应仓库维护权限的贡献者）也不是首次贡献的前提。

阅读、练习和真正的开发实践不是一回事。每天几分钟的课程用于逐步建立概念；后续构建、排错和贡献还需要实际操作与投入。本课程规划的是准备路径，不承诺固定时间内一定能独立开发或让补丁合并。

## 简图或例子

假设出现“某程序读取文本时显示内容异常”。目前这只是练习情境，不是已发生或已测量的问题。调查前先写下可复现条件与结果，再查证实现，而不是先猜测并修改代码。

## 今天动手

为上述假设情境填写四项：环境/版本、复现步骤、预期结果、实际结果。实际结果写“尚未观察”，不要编造输出。

## 自检

1. 最小复现记录至少需要哪些信息？
2. 为什么看懂一段源码还不能证明补丁正确？

<details>
<summary>参考答案要点</summary>

1. 至少说明环境和版本、可执行的复现步骤、预期结果及实际结果；还可附日志和判定方法。
2. 源码阅读只是分析依据；还需要通过与问题相关的测试或观察验证修改，并考虑回归影响。真实贡献还需按目标仓库流程接受评审。

</details>

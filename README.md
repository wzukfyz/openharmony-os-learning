## 适合谁

- 学过大一程序设计基础，能读写简单 C/C++ 程序，接触过指针、结构体和函数。
- 会使用 Linux 基础命令、文件路径及编译运行程序的方法。
- 对操作系统可以没有基础，也可以学过概念但尚未读过内核源码。
- 希望理解通用内核机制，最终参与 OpenHarmony 标准系统相关开发。

不要求事先精通汇编、计算机组成原理或全部 C 语言细节。必要知识会在对应主题前引入；不重复讲授变量、循环等编程入门内容。

## 我们学习什么

```text
认识 OpenHarmony 与内核定位
        ↓
观察程序如何请求操作系统服务
        ↓
Linux 系统调用、进程、调度、内存、VFS 与同步
        ↓
构建、调试、测试和缺陷复现
        ↓
OpenHarmony 标准系统的内核配置、补丁与集成
        ↓
专题学习、小型贡献与社区评审
```

课程不以单片机、外设控制和板级驱动为主线。OpenHarmony 并非只有内核，课程也会区分 Linux 内核、系统服务、应用框架以及商业 HarmonyOS 的不同定位。

## 建议学习路线

以 365 天为完整目标，前 180 天形成基础闭环。月份是建议节奏，不绑定自然日期；具体每日选题在编写课程总目录时细化。

| 建议阶段 | 主题 | 主要成果 |
| --- | --- | --- |
| 第 1 月（含先导课） | 内核认知与行为观察 | 分清程序、进程、内核，观察系统行为 |
| 第 2 月 | 系统调用与内核入口 | 跟踪一次用户程序请求，认识源码结构 |
| 第 3 月 | 进程与线程 | 理解创建、退出、资源共享和任务对象 |
| 第 4 月 | 调度与时间 | 解释阻塞、唤醒、切换及时间机制 |
| 第 5 月 | 虚拟内存 | 理解地址空间、缺页、映射与写时复制 |
| 第 6 月 | 文件与 VFS | 串联文件打开、读取与关闭 |
| 第 7 月 | 并发与同步 | 理解竞态、锁和对象生命周期 |
| 第 8 月 | 构建、启动与调试 | 运行实验内核，形成定位问题的方法 |
| 第 9 月 | 测试与缺陷复现 | 运行测试，形成可复现的问题记录 |
| 第 10 月 | OpenHarmony 内核集成 | 理解内核基线、配置、补丁与构建关系 |
| 第 11 月 | 专题源码与补丁阅读 | 聚焦调度、内存、VFS 或测试等一个方向 |
| 第 12 月 | 贡献实践与复盘 | 准备小型贡献，记录验证和评审过程 |

构建与调试在第八阶段系统讲解，但实验从前期就开始：先观察普通 Linux 的行为，再进入实验内核；不必先等待完整 OpenHarmony 构建环境就绪。

## 每天怎样学

1. **阅读 5～15 分钟**：围绕一个问题理解一个主要概念。
2. **回答自检问题**：先自己解释，再查看参考答案。
3. **完成微练习**：通常 1～5 分钟，观察输出或验证一个判断。
4. **按需安排扩展实验**：复杂实验另列耗时，拆成多天检查点。

每周安排复习或自测。漏学后从下一篇继续，不要求追赶自然日期，也不把连续打卡作为掌握知识的证据。

### 时间与能力预期

5～15 分钟是正文阅读时间，不包含源码下载、环境安装和编译等待。只读也能逐渐建立知识框架；进入构建、测试和贡献阶段，需要实际运行、排错和验证的时间。

半年目标是理解常见机制并完成基础实验；一年目标是具备准备一份小型贡献的能力。进度随实践投入调整，不承诺固定时间独立开发或补丁必然被合并。

## 如何判断学会了

学习记录应区分“阅读完成”“实验完成”和“验收通过”：

| 检查点 | 能力证据 |
| --- | --- |
| 基础认知 | 用自己的话解释程序、进程、Shell 与内核的区别 |
| 半年基础闭环 | 结合实验解释系统调用、阻塞唤醒、虚拟内存和文件访问 |
| 测试阶段 | 写清环境、复现步骤、预期结果和实际结果 |
| 贡献阶段 | 给出修改依据、验证结果及适用范围，并回应评审问题 |

测试、文档修正或可复现的小缺陷都可以成为起点。提交贡献不以获得 Committer 身份为前提；未合并的补丁也可以形成有价值的学习记录。

## 本地版本管理

Git 仓库根目录为本目录。交接记录采用 `YYYYMMDD_HHMMSS_交接文档.md`，通过任务编号和状态区分当前任务与历史记录。

空目录中的 `.gitkeep` 仅用于保留课程目录结构，不代表课程正文；写入实际资料后可移除对应标记。

在本目录执行 `git status` 查看修改，`git diff` 查看未暂存修改，`git diff --cached` 查看暂存内容，`git log --oneline` 查看回档基线。初次提交后的新增文件需先用 `git status` 识别；普通 `git diff` 不显示未跟踪文件内容。恢复文件前先确认目标提交与需要保留的改动。
